## D4. Spec ambiguities resolved in slice 1 (owner to review)
1. **Free cash semantics**: `free_unencumbered_cash_usd` from the snapshot is treated as already net of collateral reserved by existing orders. Gate: `free_cash >= new collateral`. If the owner's number is gross, this under-blocks; the daily snapshot prompt must say "free for NEW puts".
2. **Drawdown latching (owner decision, supersedes earlier level-based 3%/5%)**: ALL levels latch (3% pause, 5% reduce-review, 8% halt). The highest level reached since the last reset stays until the owner runs `Journal.record_risk_reset`; a rebound never re-enables entries. Exit and position monitoring keep running while latched. Reset moves the drawdown cut-off to the latest confirmed snapshot and the original baseline stops seeding the peak.
3. **Baseline (owner decision)**: the owner confirmed $100,000 starting equity. It is recorded as an explicit audited journal event (`BASELINE_CONFIRMED`, with timestamp) via owner-run `csp-alerts journal confirm-baseline --equity 100000` (once only; the CLI warns if it differs from policy `account_reference_value_usd`). Peak = max(baseline, all confirmed snapshots), so a first $85K snapshot reads 15% and latches HALT. With no baseline event (and no risk reset) entries stay blocked: reconcile issue `NO_BASELINE` -> `LEDGER_UNRECONCILED`. With no confirmed snapshot the drawdown state is UNKNOWN (blocked via `LEDGER_STALE`).
4. **DRAWDOWN_PAUSE** is emitted for both 3% and 5%+ (not-halt) levels; the level is in `metrics.drawdown_level`. HARD_HALT code for 8% or a latch.
5. **Aggregate caps**: `aggregate_equity_risk + new <= 25,000` and `put_collateral + new <= 25,000` both map to `NORMAL_EXPOSURE_LIMIT`; pilot `put_collateral + new <= 15,000` maps to `PILOT_COLLATERAL_LIMIT` (applies to put collateral only, aggregate stays at $25K, per the spec's policy consistency rule). The $30K emergency ceiling is only an informational flag (`emergency_breached`), never headroom.
6. **Reason codes added beyond spec 6.3 list**: `STALE_LAST_TRADE` (last print older than 1.5 days OR missing: spec 15.1 item 13 says a missing last print blocks) and `STRIKE_NOT_BELOW_SPOT`. Spec 4.4 requires these gates but lists no code. `reasons.SPEC_REASON_CODES` is the exact spec list.
7. **Decision mapping**: all gates failing -> `BLOCKED`; `DATA_UNAVAILABLE` only when `MISSING_MARKET_DATA` is present and the remaining codes are all market-data codes (or no observation at all); `MORE_RESEARCH` reserved for AI-unavailable; `PASS_VERIFIED_DATA` only for a Tier V observation with a quote timestamp no older than 120 s (and not in the future), otherwise `PASS_RESEARCH_ONLY`. Unknown earnings from the provider is a caution, but owner event clearance through expiration (<=7 days old review) is always required (`EVENT_UNVERIFIED`).
8. **ADJUSTMENT_REVIEW reserves collateral** (conservative; spec list of reserving states has four), freezes entries, and (owner decision) IS monitored: TIME_EXIT, ASSIGNMENT_REVIEW (DTE<=7 / ITM), DATA_ISSUE and price triggers where a valid quote exists, plus an extra URGENT `ADJUSTMENT_REVIEW` notice that the contract may be non-standard so every number needs manual verification. `ASSIGNED_PENDING_RECONCILIATION` does not reserve collateral (spec) but freezes entries; the linked stock lot is counted once, in `ASSIGNED_RECONCILED`.
9. **Extra state transitions** not drawn in spec 5.2 (needed for a usable ledger): DRAFT->CANCELED, PENDING->OPEN (immediate fill), CLOSE_WORKING->OPEN (closing order canceled), CLOSE_WORKING->EXPIRED/ASSIGNED_PENDING_RECONCILIATION/ADJUSTMENT_REVIEW, and ADJUSTMENT_REVIEW -> OPEN/CLOSE_WORKING/CLOSED/EXPIRED/ASSIGNED_PENDING_RECONCILIATION. Terminal states have no exits. Partial fills are rejected in v1 (`fill_contracts` must equal `contracts`).
10. **Ledger-change tracking**: audit events `POSITION_CREATED/POSITION_TRANSITION/STOCK_LOT_ADDED/POSITION_IMPORTED` mean "a trade changed"; a manually confirmed snapshot dated at/after the latest such event is then required (LEDGER_UNRECONCILED otherwise). DRAFT creation, stock re-marking, approvals and snapshots do not count.
11. **Exit monitoring**: stale-quote cutoff defaults to 2 x `exit_monitor_interval_minutes` (30 min); untimed quotes are stale. ITM (spot < strike on any quote) raises `ASSIGNMENT_REVIEW` at any DTE; DTE <= 7 raises it regardless. Profit/loss boundaries use cross-multiplication (exact) with ask, never mid. Fees are shown in net P&L but do not change trigger thresholds (spec formulas exclude fees).
12. **Config strictness**: YAML floats are rejected for Decimal fields (decimals must be quoted strings); safety flags (no margin, no naked options, no broker, AI cannot override, dry-run default, no inbound commands, etc.) are `Literal` types so editing the YAML cannot loosen them. Budget numbers stay editable but must satisfy `pilot <= normal <= emergency`.
13. **Environment (owner decision: allowlist posture, scoped)**: `CSP_DISABLE_BROKER_ACCESS` unset defaults to `true` (the only legal value); any false value is a startup error. Any non-empty variable with a broker prefix (`boundary.BROKER_ENV_PREFIXES`: SCHWAB, IBKR, IB_, MOOMOO, ALPACA, TRADIER, TASTYTRADE, ROBINHOOD, ETRADE_, FUTU_, WEBULL_, TOS_, TDA_) is a startup error (except CSP_/TELEGRAM_ names). Other credential-looking names (containing KEY, TOKEN, SECRET, PASSWORD, PASSWD, CREDENTIAL, ACCOUNT, OAUTH, CLIENT_ID, API) only produce a `doctor` WARNING (names only, never values) unless on the documented OS/tool allowlist in `settings.py` (PATH, USERPROFILE, APPDATA, PYTHON*, VIRTUAL_ENV, ...), so normal Windows/CI environments are not rejected. `CSP_ENV` accepts `paper` or `real` (spec names only `paper`; `real` is my assumption). Placeholder `REPLACE_LOCALLY` is treated as "not configured".
14. **Approved whitelist storage**: ships as empty `config/approved.json` (loader) and is mirrored into the `approved_underlyings` table by `Journal.upsert_approved`; The loader's example guard is content-based: it rejects `synthetic: true` (file or entry), ticker `EXAMPLE`, or marker words (synthetic/fictional/example only/placeholder) in `ownership_reason`, regardless of filename; `Journal.upsert_approved` rejects `synthetic` entries. Unknown asset type for a ticker not in the whitelist counts as an individual company (conservative).
15. **CSV import** accepts positions only (state-consistency checked, never overwrites an existing `trade_id`); stock lots, snapshots and approvals are entered through the Journal API now and CLI commands later. Imports record `POSITION_IMPORTED` and so require a fresh snapshot afterwards.
16. **Python**: spec says 3.12+; machine has 3.14.8 and tests ran there only. `uv` was not on PATH; installed into the project `.venv` via pip (`pip install uv` available). 3.12 not tested.
17. **Tester defect fixes (post-slice)**: (D1) sector/correlation-bucket labels are normalized with strip+casefold on write (`PutPosition`, `StockLot`, `NewPosition`, `ApprovedUnderlying`, hence CSV import) and again on compare in `policy/portfolio.py`. (D2) missing `last_option_trade_at_utc` now blocks with `STALE_LAST_TRADE` (supersedes the earlier "caution only" choice). (D3) CSV import quarantines `closed_at_utc` on DRAFT/PENDING/WORKING/OPEN/CLOSE_WORKING/ADJUSTMENT_REVIEW rows and EXPIRED rows closed before expiration. (D4) `evaluate_entry` raises `TypeError` for float/str/bool money or count inputs; NaN/Infinity credit/debit/fees raise `TransitionError`; NaN/Infinity snapshot, lot or mark values raise `JournalError`.
18. **Alert templates must compute DTE from dates** (expiration minus exchange-local date at send time), never hard-code a DTE (the spec 9.3 sample text "36 DTE" is illustrative only).

### D6 continued: checkpoint B (manual-ledger CLI, scheduling, docs)
43. **Preview by default**: every ledger command (`journal snapshot|approve|add-trade|fill|cancel|close|expire|assign|reset|record-cash-flow`, top-level `daily-check-in`) prints a preview and writes nothing unless `--apply` AND a non-empty `--reason` are given. Applied commands add a `MANUAL_COMMAND` audit event (actor via `--actor`, default `owner`, plus reason/args) on top of the journal's own events. After commitment-changing commands (add-trade other than DRAFT, fill, cancel, close, expire, assign, record-cash-flow) the F3 reconciliation prompt is printed. The CLI only records what the owner did; it cannot trade.
44. **Daily check-in (F2)** shows positions/orders/lots/last snapshot/expected collateral/open issues, then needs `--equity`, `--free-cash` (NET) and `--ack-reconciled` to write a confirmed snapshot (and optional `--mark LOT=PRICE`). It rejects free cash + active put collateral > equity (`CASH_INCONSISTENT`) in the CLI as well as in reconcile.
45. **IT-007 minimal**: `add-trade` rejects contracts != 1 and multiplier != 100 with a clear message; any collateral-reserving position already in the journal with contracts != 1 (e.g. via CSV) raises reconcile `MULTI_CONTRACT_POSITION` (-> `LEDGER_UNRECONCILED`) and freezes entries. CSV import itself still accepts such rows (it is the reconcile rule that freezes), to avoid hiding them.
46. **F4 assignment**: step 1 `assign` (OPEN/CLOSE_WORKING/ADJUSTMENT_REVIEW -> ASSIGNED_PENDING_RECONCILIATION, obligation stays visible, entries frozen); step 2 `assign --shares --cost-basis-usd [--price --fees]` calls `Journal.complete_assignment`, ONE transaction that inserts the linked lot and moves the put to ASSIGNED_RECONCILED (collateral released, shares counted once; any failure rolls back both); step 3 daily check-in. Lot id is `LOT-<trade_id>`; `--cost-basis-usd` is total cash paid; fees are added to the position's fees; the lot's reference price defaults to the strike and must be re-marked at the next check-in.
47. **IT-008 cash flows** (versioned policy behavior, recorded here): `journal record-cash-flow --amount +/- --date --note` (preview shows peak and level before/after). The flow is an audited `CASH_FLOW` event, counts as a ledger change (new snapshot needed) and shifts the drawdown peak by the amount for snapshots taken STRICTLY AFTER the moment it was recorded (the `--date` is informational). Because past snapshots are never recomputed with a later flow, and the reported level is the highest ever reached since the last reset, a flow can never clear or downgrade a latched level; only `reset` does. Peak cannot go below zero. Consequence: record a withdrawal BEFORE the check-in that first reflects it, otherwise that snapshot reads as a loss (fail closed).
48. **Reset** requires `--reviewed`, `--reason` and `--apply`; it re-baselines to the latest confirmed snapshot (existing behaviour of `Journal.record_risk_reset`).
49. **Approvals CLI**: `journal approve` edits `config/approved.json` (validated model, atomic replace, `.json.bak` copy, never accepts synthetic/example markers) including `standard_deliverable_confirmed_on`; there is no remove command (edit the file). The scan mirrors the file into the DB.
50. **Scheduling (ops/windows)**: `register-tasks.ps1` previews by default; `-Apply` registers (current user, interactive logon, wake-to-run, 10 min limit, ignore overlapping); `-Send` adds `--send` to the commands (sending still needs CSP_DRY_RUN=false and a pinned chat). Refuses unless the PC time zone is Central (Task Scheduler uses local time). ### D6 continued: tester slice-3 fixes and hardening
62. **Send classification by phase (D1)**: urllib wraps connect/send-phase failures (refused, DNS, connect timeout, no network after a PC wake) in `URLError`; those are now RETRY (nothing was processed). 63. **Part ordering (D2)**: flush order is severity, creation time, then message group and part number. If a part is not delivered (retry, unknown, failed) the later parts of that message wait, so parts never arrive out of order.

65. **Requeue (a)**: a dedup key whose previous row ended DROPPED_EXPIRED, DROPPED_STALE or FAILED_FINAL may be queued again; the existing row is reset to PENDING in place (same stable alert_id, attempts 0, new content; audited `ALERT_REQUEUED`). ### D18. Latest-attempt failures per stock and per exact contract (RV-20261031-01, RV-20261031-02)
Status: implemented and unit-tested (`tests/unit/test_latest_evidence.py`); the reviewer's `independent_market_checks.py` exits 0. Not independently re-verified. No migration (LATEST_SCHEMA stays 0005), no new dependency, no broker access, no `float`.

172. **Root cause.** `store_chain` keeps the prior stock row when the new rows carry no single consistent spot and keeps the prior option row when the new quote is not two-sided. Both were silent: nothing recorded that the NEWEST attempt failed, and `record_attempt` counts any written option row as symbol success. The retained value therefore looked current to the gates, `entry_review` and `position_view`.
173. **Design (reuse, no new table).** `observations.store_chain` records the newest-attempt failure inside the same transaction in `md_symbol_status.detail_json["latest_evidence"]`: `{"stock": {"at","reason"}, "contracts": {"<expiration>|<canonical strike>": {"at","reason"}}}`. `at` is the retrieval time of the failed attempt; `reason` is canned text. A valid stock price clears `stock`; a valid written option row clears that contract; contracts absent from a fetch keep their mark; marks for contracts pruned as expired are dropped. `record_attempt` preserves the key across its status upsert and `touch_success` already preserves the detail, so the monitor path (which also calls `store_chain`) is covered. A minimal status row is created only when a failure must be remembered and no row exists yet. A new table or a column on `md_option_latest` was rejected: it would change the 0005 schema that the acceptance migration tests and `LATEST_SCHEMA` pin.
174. **Read side (`csp_dashboard/views.py`).** A mark is active only while it is NEWER than the retained observation it qualifies (`at > retrieved_at_utc`), so it cannot outlive a valid write. (a) Stock: `_symbol_block` adds `stock_failure`, passes `attempt_failed=True` to `describe_state` (label STALE, note names the rejected evidence), and keeps the prior price with its true retrieval time. `market_detail` then treats every candidate of that symbol as not evaluated: gate marker NOT_EVALUATED and `review.all_pass` false; put rows, bids/asks and their own provenance still display. No row is chosen or averaged to repair the contradiction. (b) Contract: the row gets `retained_unusable` text, gate NOT_EVALUATED, `all_pass` false; other strikes are untouched (control: strike 42 stays eligible). (c) Position: `_latest_quote` sets `identity_problem` on the chosen quote when a newer contract failure exists; `evaluate_exits` already turns that into a DATA_ISSUE (no PROFIT_EXIT / LOSS_REVIEW / DELTA_REVIEW, `pnl` is None, `price_check` is "unavailable" with the reason and the evidence marked `retained_unusable`, original timestamp kept). The spot on the retained quote is still used for the conservative ITM assignment warning and the DTE-based TIME_EXIT/ASSIGNMENT_REVIEW signals still fire, so there is no blanket suppression. The monitor's alert path already evaluates the in-memory fresh quote (an invalid one is DATA_ISSUE), so it needed no change.
175. **Success accounting.** `last_success_at_utc` still advances when option rows were genuinely written (they are real, timestamped observations); the run stays PARTIAL as before. The stock-specific failure is carried separately, so the shared success time can no longer make the stock look healthy. Recovery (consistent spot, valid quote) clears the marks and the state returns to normal (tested: good, invalid, recovered for stock, for a candidate contract and for a held contract).
176. **Limits.** A contract that disappears from a successful chain (not the same as an invalid quote) is not marked; it ages to STALE through the normal cadence. `webtrade` (record-sold-put quote lookup) and `policy/browse.py` read the stored row directly and do not consult the mark; the market page that feeds them marks the row unusable, but a trade form opened for that exact contract was not changed in this slice. B2-3b (half-cent `templates.usd`) was not touched.

### D19. Whole-fetch failures and evidence ordering (RV-20261031-03, RV-20261031-04)
Status: implemented, unit-tested (`tests/unit/test_latest_evidence.py`); the reviewer's `additional_evidence_checks.py` and `independent_market_checks.py` exit 0. No schema change (LATEST_SCHEMA 0005 pin untouched; no acceptance test breaks).
179. **RV-03 whole-fetch failure.** `views._latest_quote` also consults `md_symbol_status`: when the newest attempt FAILED (`last_attempt_at_utc` later than `last_success_at_utc`, i.e. provider error, rate limit or empty chain, all recorded by `record_attempt(success=False)`) and is later than the retained quote's retrieval time, the quote gets an `identity_problem`, so `evaluate_exits` returns DATA_ISSUE: no P&L and no PROFIT_EXIT/LOSS_REVIEW/DELTA_REVIEW; the price check shows the reason and the original values/time; TIME_EXIT and assignment signals still fire. A later valid write (refresh or monitor via `touch_success`) moves `last_success` past the failed attempt, which restores normal state; a contract with its own newer valid evidence is never affected because its retrieval time is later than the failed attempt. Monitor-side fetch errors are not stored in the status table; the monitor already yields no quote and DATA_ISSUE itself.
180. **RV-04 ordering without a schema change.** (a) Marks now store a sub-second `at` (ISO with microseconds). In `store_chain`, any row whose stored `retrieved_at_utc` is later than the incoming fetch, or whose contract mark is later than the incoming fetch, is ignored (counted in `options_older_ignored`); the same rule protects the stock row/mark, and an older fetch never marks a row absent. So a delayed MONITOR write cannot replace newer rows, regress the stock time or clear a newer failure. Ties within one stored second are treated as not older. (b) Each mark also records `row_run`, the run id of the exact retained row it qualifies. `observations.mark_active` treats a mark as active when `row_run` matches the row OR its precise `at` is later than the row time, so a failure 500 ms after a quote in the same truncated second still invalidates it. Retrieval time is never copied into any quote/market timestamp. Rejected: a monotonic revision column (needs migration 0006 and would break the pinned schema tests).
181. **Expiry cap.** An expiry that drops out of the nearest-8-expiry cap (or outside the fetch window) is neither updated nor marked: its stored rows keep their original times and age to STALE through the normal cadence, and no "absent" mark is written for it (marks are only written for expiries the successful fetch returned). Same limit applies to a whole expiry vanishing.

### D19 addendum: RV-ACC-06, RV-ACC-07, RV-ACC-08
182. **RV-ACC-06.** `observations.touch_success` never moves `last_success_at_utc` backwards (an older or same-second success is a no-op) and, when the newest refresh ATTEMPT is later than the success being recorded, it only advances `last_success` and leaves status, error, failure counter and backoff alone. It sets status OK and clears failure/backoff only when the success is not older than the last attempt (unchanged behaviour for the normal case). A delayed older writer therefore can no longer make the market page report a failed newest attempt.
183. **RV-ACC-07.** The monitor's own fetch error is recorded by `observations.record_monitor_fetch_failure` as a whole-fetch mark (`latest_evidence["fetch"]`, precise time, canned reason, source MONITOR), never touching `last_attempt`, the failure counter or `next_attempt_after_utc`: those drive the refresh cadence and a monitor error must neither delay nor accelerate it. `views._latest_quote` treats a retained quote older than that mark as not current (DATA_ISSUE, no numeric advice); `_symbol_block` shows the symbol as failed. Any later successful `store_chain` (refresh or monitor) clears the mark. No send path is involved; the monitor's own alert behaviour is unchanged. If no status row exists yet a minimal one is created (status PARTIAL, no attempt time).
184. **RV-ACC-08.** The detail_json of the symbol status also keeps `run_at` (run id to precise retrieval time, last 50 runs), separate from `latest_evidence`. The older-write rule in `store_chain` compares the incoming fetch with the retained row's PRECISE time when its run is known (whole-second time otherwise), so a failure at 15:05:00.5 arriving after a valid quote at 15:05:00.9 is ignored, while a failure at .95 or at .5 after a quote at :00.0 still invalidates. Limit: rows older than the 50 most recent runs, or written before any status row existed, fall back to whole-second ties (tie = not older).
