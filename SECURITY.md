# SECURITY

## Contract (testable)
The app MAY: request public market data (Yahoo via Stockpile), read the owner's manual records, calculate, store local records, and send advisory Telegram messages to ONE owner-pinned private chat.
The app MUST NOT: authenticate to or import any brokerage/trading SDK, read broker balances, load trading credentials, build or submit orders, accept instructions from Telegram, change risk limits by itself, or let a model/AI override a gate. Every trade, fill, cancel, assignment and cash flow is typed in by the owner.

## How it is enforced
- `src/csp_alerts/boundary.py` lists forbidden modules/prefixes; unit and acceptance tests audit `src` statically (imports, dynamic imports, order-like names) and at runtime (loading the Stockpile adapter loads no schwab/moomoo/streamlit/trade modules). Dependencies contain no broker SDK.
- Startup validation: `CSP_DISABLE_BROKER_ACCESS` must be true; any non-empty env var with a broker prefix (SCHWAB, IBKR, IB_, MOOMOO, ALPACA, TRADIER, TASTYTRADE, ROBINHOOD, ETRADE_, FUTU_, WEBULL_, TOS_, TDA_) is a startup error; other credential-looking names produce a warning in `doctor` (names only).
- Policy safety flags (no margin, no naked options, no broker, AI cannot override, dry-run default, no inbound commands) are `Literal` types: editing the YAML cannot loosen them.
- No inbound Telegram path exists: no polling, no webhook, no open port. Outbound only: `sendMessage`, plus one `getChat` at setup.
- Send safety: dry-run is the default. A send needs `--send` AND `CSP_DRY_RUN=false` AND no `--dry-run` AND token+chat id AND a pinned private chat whose hash matches `TELEGRAM_CHAT_ID` (re-checked at flush). Dry-run never writes sendable outbox rows. Entry alerts expire (30 min) and are revalidated before sending.

## Secrets
- Only `.env` (git-ignored) holds `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. They are wrapped so they never appear in `repr`, errors, logs, audit rows or outbox evidence; error text and alert text pass through redaction (bot-token-shaped strings are replaced). The chat id is stored only as a SHA-256 hash.
- The token appears only inside the private URL builder of `alerts/telegram.py`; HTTPS is enforced (loopback HTTP is possible only with an explicit test-only flag).
- Never paste the token into a chat, ticket, screenshot or AI prompt. Rotate via @BotFather if exposed (RUNBOOK section 8).
- Keep `.env`, `data\` (journal, backups, locks) and any exports out of version control and cloud-sync folders; restrict the folder to your Windows user. Private Telegram chats are not end-to-end encrypted: messages carry limited trade detail and never full account numbers or equity totals.

## Data integrity
SQLite with WAL, transactions, an append-only audit log (UPDATE/DELETE are blocked by triggers), exact Decimal storage as text, and one writer at a time (single-instance job lock). CSV imports quarantine bad rows instead of correcting them. Backups use the SQLite online backup API.

## Known residual risks
Yahoo data is indicative and can be wrong or throttled; alerts are advisory and do not limit losses; Telegram delivery is at-least/at-most-once ambiguous (UNKNOWN_ACK is never auto-resent); the PC being off silences alerts; a compromised PC or `.env` exposes the bot (not any brokerage). Stockpile is third-party code under CC BY-NC 4.0, pinned by SHA and imported only by `market/stockpile.py`.

Report a suspected issue by revoking the bot token first, then reviewing `audit_log` (`csp outbox`, `csp status`).

## Local dashboard (`csp_dashboard`; browsing is read-only; audited writes: watchlist, refresh requests, trade/check-in recording)
- Separate package and process. `csp_alerts` still has no server socket and no inbound path; the dashboard binds only `127.0.0.1` (a non-loopback host raises at construction) and accepts only `Host: 127.0.0.1:<port>` or `localhost:<port>`.
- Views are GET-only and GETs never write. POST routes are exactly `/login`, `/logout` and the Stage A writes `/watchlist/add`, `/watchlist/remove`, `/market/refresh-request` (pinned by `server.WRITE_PATHS` and a unit test). Every POST requires a same-origin `Origin` header. No CORS headers are ever sent; cross-site `Sec-Fetch-Site` is refused. Cookies are `HttpOnly; SameSite=Strict`; sessions are random tokens in memory. Five failed logins lock sign-in for 60 seconds.
- The password is never stored: `.env` holds `CSP_DASHBOARD_PASSWORD_HASH` (salted scrypt). It never appears in a URL, page, log line or error. Request logs contain only method, path (no query string) and status.
- Data access goes through `csp_dashboard/readonly.py`: SQLite opened `mode=ro` with `PRAGMA query_only=ON` and an authorizer that denies everything except reads, one read transaction per request. Routes take no path, SQL or file name; filters are validated and bound as parameters. Database and policy file paths are never shown.
- All untrusted text (notes, alert text, reasons) is HTML-escaped and stripped of control/bidi characters. No JavaScript, no third-party or CDN assets, no analytics; CSP is `default-src 'none'; style-src 'self'`.
- Plain HTTP on loopback is acceptable for a single-user local page; do not forward the port, expose it on a LAN or put it behind a tunnel without a separate security decision (WEB-LATER).
- **Stage A writes** (watchlist add/remove, refresh request): authenticated session AND a per-session CSRF token (HMAC of the session token with a per-process key; a token from another session or none is refused with nothing written), Origin/Host/`Sec-Fetch-Site` checks, form content type and a 2 KB body bound, then POST-redirect-GET with a fixed message code (no user text is ever reflected). Add/remove are idempotent, so a double submit or replay changes nothing and is audited once. Symbols are validated (`^[A-Z][A-Z0-9.-]{0,9}$`) and hostile text is rejected, never stored or echoed. All writes go through one small module, `csp_alerts/journal/webwrites.py` (three functions, own connection and transaction each, an `audit_log` event each; it never creates or migrates the journal and has no network, Telegram or ledger access). The dashboard package itself still contains no write SQL, no Telegram transport, no network client and no subprocess.
- **Refresh requests never cause web-process network I/O**: the web writes a row (`md_refresh_requests`); the separate `market-refresh` job reads it. Rate limits: 1 per minute, 10 per hour, one pending at a time.
- **`market-refresh` job**: writes only `md_*` market-data/run tables (a test compares every other table before and after); no send path, no outbox, no ledger, snapshot or audit write; its provider error text is control-character stripped, verdict-wording neutralised and truncated before storage, and escaped again on render. Network egress stays confined to `market/stockpile.py` (Yahoo) as before.
- Hostile ticker text, stored error text, contract ids from a provider and `msg=` query values are all treated as untrusted: escaped on render, `msg` is a closed whitelist.
- **Stage B1: the dashboard now writes the LEDGER (trades and account snapshots).** Threat model: a hostile web page in the owner's browser, another local user or process, a replayed or double-submitted form, a stale page, hostile pasted text, a mistaken or tampered number. Controls, all required together for any ledger write: (1) authenticated session; (2) per-session CSRF token; (3) Origin/Host/`Sec-Fetch-Site` checks (loopback only, no CORS); (4) a two-step flow where the preview POST writes nothing and the confirm POST needs a signed preview token (HMAC with a per-process key over the session, the exact normalized fields, the ledger revision and the policy hash; 20 minute expiry; any changed field, session or ledger state is refused with a fixed message and nothing written); (5) a one-time idempotency key recorded in the audit log in the same transaction as the write (duplicate submits return the first result); (6) one transaction for create + transitions + audit events (a failure rolls everything back); (7) all rules reused from the backend (`Journal`, state machine, entry/portfolio gates, shared cash/timestamp rules) so the web layer cannot loosen them; (8) an explicit reason and acknowledgement boxes; (9) free text (reason, labels) is control-character stripped, length limited and escaped on render; (10) all errors are fixed phrases (no exception text, no paths). New POST routes: `/trade/preview`, `/trade/confirm`, `/checkin/preview`, `/checkin/confirm` (`server.TRADE_WRITE_PATHS`, 6 KB body limit); GET pages for the forms never write. Records carry actor `web:owner`, source `web`. The writer is `csp_alerts/journal/webwrites.py` (delegating to `journal/webtrade.py`); the dashboard package still has no write SQL, no Telegram transport, no network client, no subprocess and no broker code. Residual risk: anyone who can use the owner's logged-in browser session on this PC can record false trades (same as anyone with the owner's shell and the CLI); the page cannot prove a trade happened (it records what the owner reports, and the owner confirms with an acknowledged reconciliation). Baseline, cash flows, risk reset, approvals and assignment remain CLI-only restricted controls.

- **Stage B2 (label correction, the only new write).** POST routes `/portfolio/labels/preview` and `/portfolio/labels/confirm` (`server.LABEL_WRITE_PATHS`; `ALL_WRITE_PATHS` is the union of every write route). Same controls as B1, all required together: authenticated session, per-session CSRF token, Origin/Host/`Sec-Fetch-Site`, form content type and body bound, signed preview token over the exact normalized fields (including a fingerprint of the labels about to be replaced, so a change between preview and confirm is refused as stale), ledger revision and policy hash with 20 minute expiry, a one-time idempotency key recorded in the same transaction, an explicit reason and an acknowledgement box, fixed-phrase results. The write changes ONLY the sector and correlation-bucket text on one ticker's live puts and stock lots and appends `LABEL_CORRECTED` (all previous values) and `WEB_LABEL_CORRECTED` audit events. It cannot change approvals, event-clearance attestations, asset type, policy, snapshots or any position's state; for an approved ticker it accepts only labels equal to the approval's. The writer is `csp_alerts/journal/webwrites.correct_labels` -> `journal/weblabels.py`; the dashboard package still has no write SQL, network client, subprocess, Telegram or broker code. The portfolio, market and alerts pages are GET-only and read the book through the read-only connection; the JSON twin has no write routes. Reflected form values have control, format, separator and private-use characters removed and are escaped.
- **Automatic breach clearing** writes only the audit event `POLICY_BREACH_CLEARED` (never positions) and only when the recorded flag no longer reproduces; unreadable approvals clear nothing (fail closed).
- Numeric and date input is parsed as ASCII digits only with a full-string match (Unicode digits and trailing newlines are refused).
